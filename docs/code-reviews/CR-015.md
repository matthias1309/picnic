## Summary

Reviewed the staged-deployment change: the single production deploy job is split
into `deploy-dev` (branch `develop` → `mattdev@jarnsaxa`), an `acceptance` stage
that runs HTTP smoke tests against the live dev deployment, and `deploy-prod`
(branch `main` → `mattmaxx@giclas`) gated by a manual approval on the `production`
GitHub environment. `scripts/deploy.sh` is parametrised via `DEPLOY_REF`
(default `main`) and `PUBLIC_BASE_URL`, with the ref-resolution logic extracted to
`scripts/deploy_lib.sh` for unit testing.

Files: `.github/workflows/ci-cd.yml`, `scripts/deploy.sh`,
`scripts/deploy_lib.sh`, `backend/tests/test_pipeline_wiring.py`,
`backend/tests/test_deploy_ref.py`, `backend/tests/acceptance/*`,
`pyproject.toml`, `requirements-dev.txt`, `docs/DEPLOYMENT.md`.

| 1 | minor | `.github/workflows/ci-cd.yml` (`deploy-prod`) | On a push to `main`, `deploy-dev`/`acceptance` are skipped, so `deploy-prod` uses `always()` + explicit `result` checks. Documented in ARCH-015 and `docs/DEPLOYMENT.md`; accepted as the consequence of the chosen `develop→dev, main→prod` model. |
