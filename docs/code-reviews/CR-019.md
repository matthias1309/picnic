## Summary

Makes the backend's `URL_PREFIX` and the frontend's `VITE_BASE_PATH` /
`VITE_API_BASE` configurable via env vars (each defaulting to today's
dev/staging value), plus a new `FRONTEND_PUBLISH_DIR` for `deploy.sh`, so
production could move off the shared path-based scheme
(`matt-maxx.de/picnic` + `/picnic-frontend/`) onto its own domain,
`https://picnic.matt-maxx.de/`, serving the frontend at the domain root and
the API under `/api`. Dev/staging (`mattdev.uber.space/picnic*`) is
unaffected — it keeps the old defaults with zero config change.

Shipped across three PRs, the last two being same-day production hotfixes
found during the actual cutover (see Findings):

- [#37](https://github.com/matthias1309/picnic/pull/37) — the REQ-019
  feature itself (`url_prefix` setting, `build_router()` extraction,
  `resolveBasePath`/`resolveApiBase`, `read_env_default`,
  `FRONTEND_PUBLISH_DIR`, `docs/DEPLOYMENT.md` cutover guide).
- [#38](https://github.com/matthias1309/picnic/pull/38) — hotfix:
  `Settings.Config` needed `extra = "ignore"`.
- [#39](https://github.com/matthias1309/picnic/pull/39) — hotfix: session
  cookie `Path` needed to track `url_prefix` at request time.

Both incidents are written up in full in `docs/architecture/ARCH-019.md`.

## Findings

Two issues escaped the original review/test pass and only surfaced during
the actual production cutover — both are now fixed, covered by regression
tests, and verified live. Recorded here rather than swept under the rug,
per this project's own "Learnings" convention.

| # | Severity | File / Line | Description |
|---|----------|-------------|--------------|
| 1 | blocker (caused a full prod outage, ~30 min) | `backend/config.py` | `Settings` (pydantic-settings) rejects any `.env` key it doesn't declare as a field by default. `VITE_BASE_PATH`/`VITE_API_BASE`/`FRONTEND_PUBLISH_DIR` are `deploy.sh`-only shell values that were never meant to be validated by `Settings`, but sharing one `.env` file meant they crashed gunicorn on boot (`ValidationError: extra_forbidden`) the moment they were added to prod's `.env`. Root design gap: ARCH-019 didn't consider that `Settings` validates the *whole* file, not just the fields it reads. Fixed in #38 (`extra = "ignore"`), covered by `test_config.py` (reproduces the exact prod traceback against a real temp `.env` file). |
| 2 | blocker (site loaded, but every authenticated view was broken) | `backend/api/auth_routes.py` | Session cookie `Path` was hardcoded to `"/picnic"`, so once `URL_PREFIX=""` moved routes to the domain root, the browser never sent the cookie back to `/api/*` — 401 on everything. Missed entirely in the original design pass (§ Key Decisions in ARCH-019 never mentions cookies). Fixed in #39 (`_cookie_path()`, computed at request time from live `settings.url_prefix`). The first version of the regression test itself had a bug — it compared against a stale module-level constant instead of the live setting, giving a false green — corrected before merging; see ARCH-019's incident 2 write-up for how the corrected test actually exercises the real code path. |

Both findings share a root cause worth naming explicitly: **the original
test suite exercised `build_router(prefix)` and `Settings(url_prefix=...)`
via direct constructor/function arguments, never through the actual
`.env`-file-driven startup path production uses.** Neither `extra_forbidden`
nor the cookie-path mismatch could have been caught by tests that never
went through `DotEnvSettingsSource` or a real `settings.url_prefix` read at
request time. `test_config.py` and the corrected cookie tests close that
specific gap for this REQ; whether it's worth a general project-level
"test the .env-driven boot path, not just constructor args" convention is
left as a follow-up, not blocking this CR.
