# REQ-019 — Serve Production Under a Clean picnic.matt-maxx.de Root URL

**Status:** draft
**Created:** 2026-08-17
**Traced by:** ARCH-019, TEST-019

## User Story

As the **account owner**,
I want **the production app reachable at `https://picnic.matt-maxx.de/` (frontend
at the domain root, API under `/api`, health check at `/health`), instead of the
current path-prefixed `https://matt-maxx.de/picnic` and `/picnic-frontend/`**,
in order to **have a short, memorable production URL without stale internal
path segments leaking into it**.

## Context

Both environments currently share one hardcoded URL scheme baked into the
code: the backend mounts every route under `APIRouter(prefix="/picnic")`
([backend/main.py:206](../../backend/main.py)), and the frontend hardcodes
`base: "/picnic-frontend/"` in the Vite build and `API_BASE = "/picnic/api"`
in the API client. This scheme is what today's dev/staging environment
(`mattdev@jarnsaxa`, `https://mattdev.uber.space/picnic-frontend/` +
`/picnic/api`) needs and **must keep** — dev is out of scope for this change.

Production, however, is moving to its own subdomain (`picnic.matt-maxx.de`,
provisioned separately on the existing `mattmaxx@giclas` Uberspace account —
DNS + `uberspace web domain add` + `uberspace web backend set`, tracked
outside this REQ as it's infrastructure, not application code). Once prod has
its own domain, the `/picnic` / `/picnic-frontend` path segments serve no
purpose there and should be dropped for that environment only.

Decision (confirmed with the user): the old path-based production URLs
(`https://matt-maxx.de/picnic`, `https://matt-maxx.de/picnic-frontend/`) are
**retired**, not kept running in parallel — there is a single backend
process on prod, and it registers routes with one prefix value at a time.

## Acceptance Criteria

### AC-019-01: Backend serves API and health check at the domain root when configured for prod

```gherkin
Given the backend is started with URL_PREFIX="" (empty)
When a client requests GET /api/stats/budget or GET /health
Then the backend responds normally (no /picnic segment required)
And GET /picnic/health returns 404 (the old prefixed path no longer exists)
```

### AC-019-02: Backend keeps today's /picnic-prefixed behavior for dev when unconfigured

```gherkin
Given the backend is started with URL_PREFIX unset (or explicitly "/picnic")
When a client requests GET /picnic/api/stats/budget or GET /picnic/health
Then the backend responds exactly as it does today
And this is the default when URL_PREFIX is not set in the environment
```

### AC-019-03: Frontend build produces a root-relative bundle for prod

```gherkin
Given the frontend is built with VITE_BASE_PATH=/ and VITE_API_BASE=/api
When the built bundle is served from the domain root of picnic.matt-maxx.de
Then asset URLs, client-side routes, and API calls all resolve under /
  (e.g. https://picnic.matt-maxx.de/stats, https://picnic.matt-maxx.de/api/stats/budget)
And no reference to /picnic-frontend/ or /picnic/api appears in the built output
```

### AC-019-04: Frontend build keeps today's /picnic-frontend/ behavior for dev when unconfigured

```gherkin
Given the frontend is built with VITE_BASE_PATH and VITE_API_BASE unset
When the build runs (as it does today in CI for the dev/staging deploy)
Then the output is byte-for-byte equivalent to today: base "/picnic-frontend/",
  API_BASE "/picnic/api"
```

### AC-019-05: Deploy script health check adapts to the configured prefix

```gherkin
Given scripts/deploy.sh runs with URL_PREFIX="" for a prod deploy
When the post-restart health check runs
Then it polls http://127.0.0.1:8000/health (not /picnic/health)
And a dev deploy (URL_PREFIX unset) keeps polling http://127.0.0.1:8000/picnic/health
```

### AC-019-06: Deploy script publishes the frontend build to a configurable directory

```gherkin
Given scripts/deploy.sh runs with FRONTEND_PUBLISH_DIR unset
When the frontend build step runs
Then the build is published to ~/html/picnic-frontend, exactly as today

Given scripts/deploy.sh runs with FRONTEND_PUBLISH_DIR set to a prod-specific
  path (the domain document root for picnic.matt-maxx.de)
When the frontend build step runs
Then the build is published to that configured path instead
```

### AC-019-07: No regression on existing backend/frontend test suites

```gherkin
Given the existing backend (pytest) and frontend (vitest) test suites
When URL_PREFIX / VITE_BASE_PATH / VITE_API_BASE / FRONTEND_PUBLISH_DIR
  default to their current values (unset)
Then all existing tests continue to pass unmodified
```

## Notes

**Out of scope for this REQ (tracked as manual ops steps, not code):**
- DNS A/AAAA records for `picnic.matt-maxx.de`.
- `uberspace web domain add picnic.matt-maxx.de` on the prod host.
- `uberspace web backend set` routing for `/api` and `/health` on the new
  domain, and the domain-specific static document root for the built
  frontend.
- Updating the `production` GitHub Environment with the new `URL_PREFIX=""`,
  `VITE_BASE_PATH=/`, `VITE_API_BASE=/api`, and `PUBLIC_BASE_URL=https://picnic.matt-maxx.de`
  values, and `CORS_ORIGINS` on prod's `.env` if it ever needs a
  cross-origin caller (same-origin fetches don't require it).

**In scope:**
- Making `URL_PREFIX` (backend) and `VITE_BASE_PATH` / `VITE_API_BASE`
  (frontend) configurable via environment variables, defaulting to today's
  values so dev/staging needs zero config changes.
- `scripts/deploy.sh` reading `URL_PREFIX` for its health check, and a new
  `FRONTEND_PUBLISH_DIR` for where the built frontend is copied, both
  defaulting to today's hardcoded values.
- All three of `URL_PREFIX`, `VITE_BASE_PATH`, `VITE_API_BASE`, and
  `FRONTEND_PUBLISH_DIR` are read from the per-host `.env` file (already the
  established, uncommitted, per-environment config file — see
  `docs/DEPLOYMENT.md`), not passed through the CI SSH command. No changes
  to `.github/workflows/ci-cd.yml` are needed.

**Explicitly not done:** dual-mounting the router at both prefixes to keep
old prod URLs alive (rejected — adds permanent complexity for a transitional
concern; old prod links are expected to break once this ships).
