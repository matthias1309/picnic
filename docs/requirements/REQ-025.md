# REQ-025 — Deploy Fails Fast on Schema Drift

**Status:** draft
**Created:** 2026-08-27
**Traced by:** ARCH-025, TEST-025

## User Story

As the **operator of the Picnic deployment**,
I want **the deploy to stop with the exact SQL it needs when the database is
missing a column the code expects**,
in order to **learn about a pending migration from a failed deploy rather than
from a broken production app**.

## Context

`scripts/deploy.sh` step 4 calls `init_db()` only when the database file does
not exist yet; on an existing database it prints "Database already exists" and
does nothing. `Base.metadata.create_all` adds missing *tables*, never missing
*columns*. There is no migration mechanism at all.

REQ-024 exposed what that costs. It adds two columns to `products`, and if the
`ALTER TABLE` is forgotten, the pipeline still reports success end to end:
`deploy-dev` finishes, Gunicorn restarts, and the acceptance gate from REQ-015
stays green — because it only checks `/health` (which never touches the
database) and that a protected route answers `401` (which returns before any
query runs). The first sign of trouble is a user hitting a products or
statistics page and receiving a 500 from
`OperationalError: no such column: products.category_key`.

This REQ closes that gap in the direction CLAUDE.md requires: migrations stay
a reviewed, human-run step, but the deploy refuses to put code on top of a
database that cannot serve it, and tells the operator exactly what to run.

## Acceptance Criteria

### AC-025-01: A matching schema lets the deploy proceed

```gherkin
Given the database schema matches the SQLAlchemy models
When the deploy runs the schema check
Then the check reports no drift
And the deploy continues to the frontend build and the service restart
```

### AC-025-02: A fresh database is not reported as drift

```gherkin
Given no database file exists yet
When the deploy runs
Then the database is initialised from the models as it is today
And the schema check reports no drift
```

### AC-025-03: A missing column aborts the deploy with the exact SQL

```gherkin
Given the database is missing the column products.category_key
When the deploy runs the schema check
Then the deploy exits with a non-zero status
And the output names the table and column that are missing
And the output contains the ALTER TABLE statement that adds it,
  including the column type
```

### AC-025-04: The service is not restarted when the check fails

```gherkin
Given the schema check has reported drift
When the deploy aborts
Then supervisorctl restart is not executed
And the previously running application keeps serving requests
```

### AC-025-05: Every difference is reported in one run

```gherkin
Given the database is missing two columns and one table
When the deploy runs the schema check
Then all three are listed in a single report
And the operator does not have to re-run the deploy to discover the next one
```

### AC-025-06: Columns the models no longer declare are not an error

```gherkin
Given the database has a column that no model declares
  (for example after a rollback to an earlier code version)
When the deploy runs the schema check
Then no drift is reported for that column
And the deploy continues
```

### AC-025-07: The check runs standalone

```gherkin
Given the operator wants to know whether a migration is pending
When they run the schema check as a standalone command against a database
Then the same report is produced
And the exit status reflects whether drift was found
```

### AC-025-08: The CI deploy job fails visibly on drift

```gherkin
Given the schema check aborts the deploy on the dev host
When the deploy-dev job finishes
Then the GitHub Actions job is marked failed
And the acceptance and deploy-prod jobs do not run
```

## Notes

**Implementation approach:**
- Derive the expectation from `Base.metadata` rather than from a hand-written
  migration list: compare each mapped table's columns against
  `PRAGMA table_info(<table>)`. Every future column is then covered without
  per-migration bookkeeping, which is exactly the gap `create_all` leaves.
- The check is a Python module so it reads the same metadata the application
  does, invoked from `deploy.sh` step 4 and runnable on its own (AC-025-07).
- Detect only; never apply. CLAUDE.md requires migrations to be reviewed by a
  human before production, and this REQ deliberately keeps that rule intact —
  the value here is the loud, early failure with an actionable message, not
  automation of the change itself.
- Failing before the restart (AC-025-04) is what makes the failure safe: the
  old workers keep serving the old code against the old schema, which is a
  consistent state. Restarting first and then discovering the drift is not.

**Rejected alternatives:**
- Applying the missing columns automatically — contradicts the CLAUDE.md
  review rule, and an automatic `ALTER TABLE` on the production database is
  precisely the class of change that deserves a human.
- An explicit numbered migration list plus a `schema_migrations` table — more
  capable (renames, type changes), but it is hand-maintained per change and
  would still not have caught REQ-024 if someone forgot to add the entry.
- Alembic — the real tool, and listed as optional in CLAUDE.md, but a large
  apparatus for a single-user SQLite app whose only unmet need is "a column is
  missing".

**Out of Scope:**
- Applying, generating or ordering migrations.
- Detecting changed column *types*, renames, dropped columns, index or
  constraint drift — only missing tables and missing columns break the running
  app today.
- Databases other than SQLite (`PRAGMA table_info` is SQLite-specific, and
  CLAUDE.md fixes SQLite as the only target).
- The second gap REQ-024 exposed — that the acceptance suite never exercises a
  database-backed route — which belongs in its own REQ.
