# REQ-012 — Robust Item-Row Detection for the Current Picnic Invoice Format

**Status:** approved
**Created:** 2026-06-16
**Traced by:** ARCH-012, TEST-012

## User Story

As the **account owner**,
I want **invoice emails in Picnic's current HTML format to be parsed into line
items**,
in order to **keep tracking my spending even after Picnic changed the styling
of its "Dein Bon" emails**.

## Context

REQ-002 parses Picnic "Dein Bon" invoice emails via `ReceiptParser`. A newly
received invoice failed to parse: `ReceiptParser.parse()` raised
`ParseError: No item rows found in invoice HTML` and no articles were stored.

Two independent root causes were identified by reproducing the failure against
the raw email:

1. **Row-style mismatch.** The parser locates article rows with the exact CSS
   substring selector `td[style*="border-bottom:1px solid #ebebeb"]`
   (`parser.py`, `_ITEM_ROW_STYLE`). Picnic's current template renders that
   declaration as `border-bottom: 1px solid #EBEBEB` — a **space after the
   colon** and an **uppercase hex value**. CSS attribute substring matching is
   exact and case-sensitive, so the selector matches zero rows.

2. **Non-product rows share the row style.** After fixing (1), the trailing
   summary blocks (`Pfand` / `Flaschen` / `Tüten`, `Eingereichtes Pfand`,
   `Lieferadresse`) also carry the `border-bottom: 1px solid #EBEBEB` style but
   contain **no product image**. `_parse_item_row` requires an `img[alt]` and
   would raise `ParseError` on these rows, aborting the whole parse.

## Acceptance Criteria

### AC-012-01: Parse line items in the current invoice format

```gherkin
Given the HTML of a Picnic invoice whose item rows use the current style
  "border-bottom: 1px solid #EBEBEB" (space after the colon, uppercase hex)
When ReceiptParser.parse() is called
Then every article row is extracted with name, quantity, and prices
```

### AC-012-02: Ignore non-product rows that share the item-row style

```gherkin
Given an invoice whose Pfand / address summary blocks carry the same
  "border-bottom" style as item rows but contain no product image
When ReceiptParser.parse() is called
Then those summary rows are not treated as items
And parsing does not raise because of them
```

### AC-012-03: No regression on existing invoice formats

```gherkin
Given the existing picnic_receipt.html and picnic_receipt_forwarded.html
  fixtures (original lowercase, no-space row style)
When ReceiptParser.parse() is called
Then all items and the stated total are extracted exactly as before
  (TC-002-03, TC-002-04, TC-002-06, TC-008-01, TC-008-02 still pass)
```

## Notes

**Implementation approach:**
- Match the item-row style with whitespace- and case-insensitive comparison
  instead of a literal CSS substring selector.
- Require a product `img[alt]` for a row to count as an item row, which
  naturally excludes the Pfand / address summary blocks.

**Out of Scope:**
- Re-parsing of already-imported receipts (manual DB step, per CLAUDE.md the
  developer resets `processed = False` and re-runs).
- Other future Picnic template changes beyond whitespace/case of the row style.
- Order-number grouping of items — see REQ-013.

**Testing Strategy:**
- New anonymized fixture `picnic_receipt_current.html` reproducing the current
  row style plus a Pfand summary row (no product image).
- Regression assertions on the existing fixtures.
- See TEST-012.
