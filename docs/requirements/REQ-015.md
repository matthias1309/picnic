# REQ-015 — Staged Deployment with a Dev Acceptance Gate

**Status:** approved
**Created:** 2026-06-17
**Traced by:** ARCH-015, TEST-015

## User Story

As the **account owner / operator**,
I want **every change to be deployed to a separate development Uberspace and pass
automated acceptance tests there before it can reach production**,
in order to **catch regressions against a real running deployment instead of
discovering them on the production instance I use daily**.

## Context

Today the pipeline (`.github/workflows/ci-cd.yml`) has a single `deploy` job that
runs only on a push to `main`, against the GitHub environment `production`, using
one set of secrets (`UBERSPACE_HOST`, `UBERSPACE_USER`, `UBERSPACE_SSH_PORT`,
`UBERSPACE_SSH_KEY`). The deploy script (`scripts/deploy.sh`) is hard-wired to
`git reset --hard origin/main`. There is **no staging step** and there are **no
acceptance tests** that exercise a running deployment — only in-process unit and
integration tests under `backend/tests/`.

A second Uberspace has been provisioned as a dedicated dev instance:

| | Production | Development |
|---|---|---|
| Uberspace host | `giclas.uberspace.de` | `jarnsaxa.uberspace.de` |
| User | `mattmaxx` | `mattdev` |
| Public base URL | `https://matt-maxx.de/picnic` | `https://mattdev.uber.space/picnic` |

The app is always served under the `/picnic` path prefix
(`backend/main.py:206`, `APIRouter(prefix="/picnic")`), so the health endpoint on
dev is `https://mattdev.uber.space/picnic/health`.

**Branch model (decided):** push to `develop` deploys to dev and runs acceptance
tests; a merge to `main` deploys to production. The production deploy is gated by
a **manual approval** (GitHub environment required reviewer) and must not start
unless the acceptance tests on dev are green.

## Acceptance Criteria

### AC-015-01: A push to develop deploys to the dev Uberspace

```gherkin
Given a commit is pushed to the develop branch
When the CI/CD pipeline runs
Then the dev deploy job runs against the development environment
And it deploys the develop ref to mattdev@jarnsaxa.uberspace.de
And the production deploy job does not run
```

### AC-015-02: Acceptance tests run against the dev deployment

```gherkin
Given the dev deploy job has completed
When the acceptance stage runs
Then the acceptance tests execute against https://mattdev.uber.space/picnic
And they assert the deployment is healthy and serves the core endpoints
```

### AC-015-03: A red acceptance run blocks the production deploy

```gherkin
Given the acceptance tests against the dev deployment fail
When the pipeline continues
Then the production deploy job does not run
```

### AC-015-04: Production deploys only from main, after acceptance, with approval

```gherkin
Given the acceptance tests against dev are green
And a commit is on the main branch
When the pipeline reaches the production deploy job
Then the job waits for manual approval in the production environment
And on approval it deploys the main ref to mattmaxx@giclas.uberspace.de
```

### AC-015-05: The deploy script targets the configured ref and host

```gherkin
Given the deploy script is invoked with a DEPLOY_REF environment variable
When the script updates the checked-out repository
Then it resets to origin/<DEPLOY_REF> rather than a hard-coded origin/main
And when DEPLOY_REF is unset it defaults to main (production-safe default)
```

### AC-015-06: Acceptance tests verify health and an authenticated-API contract

```gherkin
Given the acceptance suite runs against a BASE_URL
When it requests <BASE_URL>/health
Then the response is 200 with status "ok"
And when it requests a protected /api route without a session
Then the response is 401 (the app is up and auth is wired), not a 5xx or a
  connection error
```

## Notes

**Implementation approach:**
- Split the `deploy` job into `deploy-dev` (environment `development`, runs on
  `develop`) and `deploy-prod` (environment `production`, runs on `main`), with an
  `acceptance` job in between (`needs: deploy-dev`).
- Parametrise `scripts/deploy.sh`: read `DEPLOY_REF` (default `main`) instead of
  the hard-coded `origin/main`; keep the internal `127.0.0.1:8000/picnic/health`
  check (identical on both hosts). Optionally surface the public base URL for the
  log output only.
- Per-environment secrets are stored on the two GitHub environments
  (`development`, `production`); the workflow references the same secret names so
  the deploy step stays generic.
- The manual production gate is a GitHub **environment protection rule** (required
  reviewer) on `production`, not workflow code.
- New acceptance suite under `backend/tests/acceptance/`, marked with a pytest
  `acceptance` marker, driven by a `BASE_URL` env var. It hits the live
  deployment over HTTP and is excluded from the normal unit-test job (no live
  server there).

**Out of Scope:**
- A separate dev *database seed / fixtures* strategy beyond an empty dev DB
  (acceptance tests only assert availability and the auth contract, not seeded
  data).
- Promotion of the *same build artifact* dev→prod (each environment builds from
  its ref; byte-for-byte artifact promotion is a later improvement).
- Blue/green or zero-downtime deploys, rollback automation beyond the existing
  `git reset` mechanism (`docs/DEPLOYMENT.md` Rollback).
- Frontend end-to-end (browser) acceptance tests — HTTP-level checks only for MVP.
- Provisioning the dev Uberspace itself (supervisord service, web backend route,
  deploy key) is a one-time manual operator step documented in `docs/DEPLOYMENT.md`,
  not automated here.

**Testing Strategy:**
- The acceptance suite is itself the executable artifact for AC-015-02/06; it is
  written to run against any `BASE_URL` and is exercised in CI against dev.
- Workflow-structure ACs (01, 03, 04) are verified by inspecting the job
  `needs`/`if` graph and the environment bindings in `ci-cd.yml`; a lightweight
  lint test asserts the job wiring so the gate cannot be silently removed.
- AC-015-05 is verified by a unit test of the deploy-ref resolution logic.
- See TEST-015.
