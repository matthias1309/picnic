# REQ-007 — Login Rate Limiting

**Status:** approved
**Created:** 2026-06-14
**Traced by:** ARCH-007, TEST-007

## User Story

As the account owner,
I want repeated failed login attempts against my account to be temporarily
blocked,
in order to protect my login credentials from brute-force guessing.

## Acceptance Criteria

### AC-007-01: Lockout after repeated failed attempts

```gherkin
Given a registered user "alice"
When 5 consecutive login attempts for "alice" with the wrong password are
     made within a 15-minute window
Then the next login attempt for "alice" is rejected with 429 Too Many
     Requests, even if the correct password is supplied
```

### AC-007-02: Successful login resets the failed-attempt counter

```gherkin
Given a registered user "alice" has some recent failed login attempts,
      fewer than the lockout threshold
When she logs in with the correct password
Then the login succeeds
And her failed-attempt count is reset, so a subsequent single wrong-password
    attempt does not trigger a lockout
```

### AC-007-03: Lockout responses do not reveal whether an account exists

```gherkin
Given an unknown username "ghost" has reached 5 failed login attempts within
      a 15-minute window
When another login attempt is made for "ghost"
Then the response is 429 Too Many Requests, identical to the response for a
     locked-out real account
```

### AC-007-04: Lockout expires automatically

```gherkin
Given a registered user "alice" was locked out, but the lockout period has
      since elapsed
When she submits a login attempt with the correct password
Then the login succeeds
```

## Notes

- Lockout is keyed by **username**, not source IP — this is a small
  household app with two known accounts, and a username-based lock is
  simpler and cannot be bypassed by switching IPs.
- Thresholds: 5 failed attempts within 15 minutes triggers a lockout for 15
  minutes. Exact values to be finalized in ARCH-007; chosen to be generous
  enough to not lock out a household member who mistypes their password a
  couple of times, while making online brute-forcing impractical.
- The existing generic "Invalid username or password" message for AC-006-02
  is unchanged; the new 429 response is its own distinct error so the
  frontend can show a different message ("too many attempts, try again
  later").
- Persisted in the database (not in-memory), since the production deployment
  runs 2 Gunicorn workers (see `docs/DEPLOYMENT.md`) and an in-memory counter
  would not be shared between them.
- Out of scope: IP-based rate limiting, CAPTCHA, account lockout
  notifications/alerts.
