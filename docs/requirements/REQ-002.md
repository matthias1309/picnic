# REQ-002 — HTML Email Parsing and Structured Receipt Storage

**Status:** draft  
**Created:** 2026-06-13  
**Traced by:** ARCH-002, TEST-002

## User Story

As a **system backend**,  
I want to **parse the raw Picnic invoice emails into structured articles, quantities, and prices**,  
in order to **turn the stored raw emails into queryable data for statistics and charts**.

## Context

REQ-001 stores the full raw MIME message in `receipts.raw_email_text` and marks
each row with `processed = False`. REQ-002 consumes those unprocessed receipts,
extracts the line items from the HTML invoice table, persists them in a
normalized schema, and flips `processed = True`.

## Acceptance Criteria

### AC-002-01: Parse line items from an invoice email

```gherkin
Given a stored receipt with raw HTML containing a Picnic invoice table
When the parser processes that receipt
Then each article row is extracted with name, quantity, unit price, and line total
And the extracted items are stored in the receipt_items table linked to the receipt
```

### AC-002-02: Maintain a product catalog

```gherkin
Given a parsed article with a product name
When the article is stored
Then a matching product row is created in the products table if it does not exist
And existing products are reused by exact name match (no fuzzy matching in MVP)
And each receipt_item references its product by foreign key
```

### AC-002-03: Record price history per item

```gherkin
Given a parsed article with a price and a receipt date
When the article is stored
Then a price_history row is recorded with product, price, quantity, and receipt date
So that price trends over time can be queried efficiently
```

### AC-002-04: Mark receipts as processed

```gherkin
Given a receipt has been successfully parsed and its items stored
When the parsing transaction commits
Then the receipt.processed flag is set to True
And the receipt is not re-parsed in subsequent runs
```

### AC-002-05: Resilient parsing on malformed emails

```gherkin
Given a receipt whose HTML does not match the expected invoice structure
When the parser attempts to process it
Then the error is logged with the receipt id and reason
And the receipt is left with processed = False (or flagged) for later inspection
And the parser continues with the remaining receipts (no crash)
```

### AC-002-06: Receipt total reconciliation

```gherkin
Given a parsed invoice with a stated order total in the email
When the sum of all line totals is computed
Then a warning is logged if the computed sum does not match the stated total
So that parsing errors are detectable
```

## Notes

**Implementation approach:**
- Parse HTML with BeautifulSoup 4 (already in the planned tech stack).
- Extract the MIME `text/html` part from `raw_email_text` using stdlib `email`.
- New tables: `receipt_items`, `products`, `price_history` (see ARCH-002).
- Parsing runs as a step after polling (same APScheduler cycle, or a separate
  task that picks up `processed = False` receipts).
- Business logic lives in `services/receipt_service.py` (KISS, thin routes later).
- Prices are stored as integer cents (avoid float rounding) — confirm in ARCH-002.

**Out of Scope (Phase 2+):**
- Fuzzy product matching / deduplication of renamed products → exact name only.
- Multi-language invoice layouts → assume current Picnic.de HTML format.
- REST API exposure of parsed data → see REQ-003.
- Re-parsing strategy / parser versioning → Phase 2+.

**Testing Strategy:**
- Unit tests: feed saved sample HTML fixtures, assert extracted items.
- Edge cases: missing price, deposit (Pfand) rows, discounts, malformed HTML.
- Integration tests: real in-memory SQLite, verify products/price_history links.
- See TEST-002 (to be created) for detailed test cases.

**Questions / Decisions Pending:**
- How are deposits (Pfand) and discounts represented — separate item type or sign?
- Are quantities ever fractional (e.g. 0.5 kg)? Decimal vs integer quantity.
- Should the parser run inside the polling task or as a separate scheduled task?
