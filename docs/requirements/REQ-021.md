# REQ-021 — Searchable Article Picker for the Price History

**Status:** approved
**Created:** 2026-08-26
**Traced by:** ARCH-021, TEST-021

## User Story

As the **account owner**,
I want **to type a few letters to find an article in the price history**,
in order to **look up what I paid for something without scrolling through a
dropdown containing every article I have ever bought**.

## Context

`PriceHistory.tsx` selects the article with a plain `<select>` populated from
`GET /products` — every distinct product ever parsed from a receipt, in
whatever order the API returns them. The list grows monotonically with every
delivery, so the control that was fine at 20 articles is unusable at several
hundred: the native dropdown renders one long scrolling column, offers no
substring search (only first-letter jump), and gives no hint which articles
are actually worth looking at.

Reported by the user as: *"Wenn ich mir die Historie eines bestimmten
Artikels anschauen möchte, darf ich ihn in einem riesigen Scrolldown-Menü
suchen."*

`ProductOut` already carries `purchase_count`, which is fetched today and
never displayed — so the data needed to rank and annotate matches is already
on the client.

## Acceptance Criteria

### AC-021-01: Typing filters the article list

```gherkin
Given the user's articles include "Bananen", "Bio-Bananen" and "Milch"
When the user types "banan" into the article field
Then only "Bananen" and "Bio-Bananen" are offered
And "Milch" is not offered
```

### AC-021-02: Matching ignores case and diacritics

```gherkin
Given an article named "Äpfel"
When the user types "apfel"
Then "Äpfel" is offered
Given an article named "Bananen"
When the user types "BANANEN"
Then "Bananen" is offered
```

### AC-021-03: Suggestions are ranked most-bought first

```gherkin
Given "Bananen" was bought 30 times and "Bio-Bananen" twice
When the user types "banan"
Then "Bananen" is listed above "Bio-Bananen"
And each suggestion shows how often it was bought
```

### AC-021-04: Selecting an article loads its price history

```gherkin
Given suggestions are shown for "banan"
When the user selects "Bananen"
Then the price history for that article is loaded and charted
And the field shows "Bananen" as the current selection
And the suggestion list closes
```

### AC-021-05: The picker is keyboard operable

```gherkin
Given the user has typed a query and suggestions are shown
When the user presses ArrowDown
Then the first suggestion is highlighted
When the user presses ArrowDown again
Then the second suggestion is highlighted
When the user presses Enter
Then the highlighted article is selected and its history loads
When the user presses Escape instead
Then the suggestion list closes without changing the selection
```

### AC-021-06: The picker is announced correctly to assistive technology

```gherkin
Given the article picker is rendered
Then it exposes the combobox role, labelled "Artikel"
And it reports whether its suggestion list is expanded
And the highlighted suggestion is exposed as the active option
```

### AC-021-07: A query with no matches says so

```gherkin
Given the user types "xyzzy"
When no article name matches
Then "Kein Artikel gefunden." is shown instead of an empty list
And no previously loaded chart is discarded
```

### AC-021-08: The selection can be cleared

```gherkin
Given an article is selected and its chart is shown
When the user clears the field
Then the chart is replaced by the "Wähle einen Artikel…" empty state
```

### AC-021-09: Existing price-history behavior is unchanged

```gherkin
Given the time-range buttons (3 Mon. / 6 Mon. / 12 Mon. / Gesamt), the
  min/max/Ø summary, the loading, error and empty states
When the picker is replaced
Then all of them behave exactly as before, driven by the same store state
  and the same API calls
```

## Notes

**Out of Scope:**
- Comparing several articles in one chart — one selected article at a time,
  as today. (Considered and deferred; would need a second REQ and a chart
  redesign.)
- Fuzzy/typo-tolerant matching beyond case and diacritic folding — CLAUDE.md
  lists fuzzy product matching as out of scope for the MVP.
- Server-side product search or pagination of `GET /products`. The full list
  is already fetched and cached by TanStack Query; filtering happens on the
  client.
- Any new dependency (no combobox library) — see ARCH-021.
