# REQ-009 — Delete a Receipt

**Status:** approved
**Created:** 2026-06-15
**Traced by:** ARCH-009, TEST-009

## User Story

As the **account owner**,
I want **to delete an individual receipt from the dashboard**,
in order to **remove erroneous, duplicate, or test receipts from my purchase
history and statistics**.

## Context

REQ-003/ARCH-003 introduced a read-only REST API for receipts
(`GET /api/receipts`, `GET /api/receipts/{id}`), and REQ-005 added the
corresponding `ReceiptList`/`ReceiptDetail` frontend views at
`/picnic-frontend/receipts`. Occasionally a receipt is imported that should
not be part of the history — e.g. a forwarded test email, a duplicate from
manual re-processing, or an email that was misclassified as a Picnic invoice.
There is currently no way to remove such a receipt; it permanently skews
statistics (REQ-004) and price history (REQ-003).

This REQ adds the ability to delete a single receipt — including its line
items and price-history entries — from the receipt detail page.

## Acceptance Criteria

### AC-009-01: Delete button is visible on the receipt detail page

```gherkin
Given the user is viewing a receipt's detail page
When the page is rendered
Then a "Delete receipt" button is visible
```

### AC-009-02: Deleting requires confirmation

```gherkin
Given the user is viewing a receipt's detail page
When they click "Delete receipt"
Then a confirmation prompt is shown
And the receipt is not deleted until they confirm the prompt
```

### AC-009-03: Cancelling the confirmation leaves the receipt untouched

```gherkin
Given the user is viewing a receipt's detail page
When they click "Delete receipt" but cancel the confirmation prompt
Then no delete request is sent
And the receipt remains visible and unchanged
```

### AC-009-04: Confirmed deletion removes the receipt and returns to the list

```gherkin
Given the user is viewing a receipt's detail page
When they click "Delete receipt" and confirm the prompt
Then a DELETE request is sent to /api/receipts/{id}
And the receipt, its line items, and its price-history entries are removed
  from the database
And the user is navigated back to the receipts list
And the deleted receipt no longer appears in the list
```

### AC-009-05: Deleting a non-existent receipt returns 404

```gherkin
Given no receipt with id 999 exists
When a DELETE request is sent to /api/receipts/999
Then a 404 response is returned
And the response body is {"detail": "Receipt not found"}
```

## Notes

**Data integrity:**
- `ReceiptItem` rows are removed automatically via the existing
  `cascade="all, delete-orphan"` relationship on `Receipt.items`.
- `PriceHistory` rows reference `receipt_id` but have no ORM relationship or
  DB-level cascade back to `Receipt`, so they must be deleted explicitly by
  the service layer to avoid orphaned price-trend data points.

**Authentication:**
- `DELETE /api/receipts/{id}` is mounted under the existing `api_router`,
  which already requires a valid session via `get_current_user` (REQ-006,
  AC-006-04). No new auth logic is needed.

**Out of Scope:**
- Bulk/multi-select deletion — single receipt only.
- Deleting `Product` rows that become unreferenced after a receipt is
  deleted — products may legitimately have zero purchases (e.g. after
  deleting their only receipt) and remain visible in `/api/products`.
- Undo / soft-delete / trash — deletion is permanent.
- Re-fetching the deleted email from IMAP to prevent re-import — out of
  scope; `message_id` deduplication (REQ-002) means a re-poll of the same
  mailbox would not re-create the receipt unless the email is removed from
  the mailbox first, which is a manual step for the developer.
