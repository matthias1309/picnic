# REQ-016 — Idempotent Receipt Parsing Under Concurrent Workers

**Status:** approved
**Created:** 2026-07-10
**Traced by:** ARCH-016, TEST-016

## User Story

As the **account owner**,
I want **each receipt to be parsed into line items exactly once**,
in order to **trust the spending statistics even when the backend runs with
multiple Gunicorn workers**.

## Context

Receipt 22 (delivered 2026-06-22) was found in production with 34
`receipt_items` — every one of its 17 real items duplicated once, all with
identical quantity, price, and order number. Re-parsing the raw email from the
IMAP mailbox against the current `ReceiptParser` produced the correct 17 items,
so the parser itself is not at fault (see REQ-012 for parser-format issues,
which this is not).

The root cause is in how the receipt is picked up for storage, not how it is
parsed:

- Uberspace runs the app via `gunicorn --workers 2`
  (`~/etc/services.d/picnic.ini`).
- `backend/main.py`'s `lifespan()` starts a **new** `BackgroundScheduler`
  inside *every* worker process. There is no coordination between workers, so
  two independent schedulers both run `parse_receipts_task` →
  `parse_pending_receipts()` on the same interval.
- `parse_pending_receipts()` (`backend/services/receipt_service.py`) selects
  all receipts with `processed == False` and, for each one, unconditionally
  calls `_store_parsed_receipt()`, which adds new `ReceiptItem` /
  `PriceHistory` rows. There is no check for whether another session already
  started (or finished) storing the same receipt.
- When a newly-polled receipt sits as `processed == False`, both workers'
  scheduler ticks can select it before either has committed. Each worker parses
  the same HTML independently (correctly) and each stores its own full set of
  items — doubling every line.

A manual maintenance one-liner run over SSH (`r.processed = False` for
receipts without items, followed by a direct call to
`parse_pending_receipts(db)`) carries the exact same risk if it happens to run
while the live scheduler's own tick is also picking up the receipt — the gap
is in `parse_pending_receipts`, not specific to the scheduler.

**Data note:** the same investigation also found single duplicated items on
receipts 13, 16, and 26. Those were checked against their raw emails and are
*not* bugs — the same product genuinely appears twice as separate line items
in the original invoice (bought twice in one order). This requirement must not
change that legitimate behavior: a receipt is allowed to contain the same
product more than once.

## Acceptance Criteria

### AC-016-01: Only one caller processes a given pending receipt

```gherkin
Given a receipt with processed == False
And two independent database sessions (simulating two Gunicorn workers) both
  attempt to claim it for processing at the same point in time
When each session attempts to claim the receipt
Then exactly one of the two claims succeeds
And the other is rejected without storing any items
```

### AC-016-02: A failed parse releases the receipt for a later retry

```gherkin
Given a receipt that has been claimed for processing
When parsing the receipt's HTML raises ParseError
Then the receipt is left with processed == False
And it is picked up again on the next parse run
```

### AC-016-03: No regression on existing single-worker parsing behavior

```gherkin
Given the existing parse_pending_receipts test suite (TC-002-07 through
  TC-002-11, TC-013-03, TC-014-04, TC-014-05)
When parse_pending_receipts(db) is called under normal, non-concurrent
  conditions
Then items, products, price history, order numbers, delivery dates,
  reconciliation warnings, and the malformed-receipt skip all behave exactly
  as before
```

## Notes

**Implementation approach:** an atomic claim (`UPDATE receipts SET
processed = 1 WHERE id = ? AND processed = 0`, checked via the affected row
count) before parsing, instead of a plain read-then-write. SQLite serializes
writers at the file level, so only one of two concurrent claim attempts on the
same row can ever see `rowcount == 1`. This fixes the bug regardless of how
many scheduler instances or worker processes exist, without depending on the
Gunicorn/APScheduler topology.

**Considered and rejected:** a `UNIQUE` constraint on
`receipt_items(receipt_id, product_id, order_number)` as a database-level
safety net. Rejected because receipts 13/16/26 show that the same product can
legitimately appear twice in one receipt — a hard uniqueness constraint would
reject real data.

**Out of Scope:**
- Making the two scheduler instances a single instance (e.g. leader election
  across Gunicorn workers). The atomic claim makes this unnecessary — it is
  correct regardless of how many workers/schedulers call
  `parse_pending_receipts` concurrently.
- Cleanup of the already-duplicated production data for receipt 22 — done
  manually ahead of this requirement (verified against the raw source email,
  17 duplicate item/price-history rows removed).
- Auditing whether receipts 13/16/26's repeated items are themselves correct
  business data beyond the raw-email cross-check already performed.
