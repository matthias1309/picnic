# REQ-008 — Fix Price Extraction for Forwarded Invoice Emails

**Status:** approved
**Created:** 2026-06-14
**Traced by:** ARCH-008, TEST-008

## User Story

As the **account owner**,
I want **invoice emails that were forwarded (e.g. via Gmail) to be parsed with
correct item prices**,
in order to **see accurate spending data even for receipts I had to forward
manually into the IMAP mailbox**.

## Context

REQ-002 parses Picnic "Dein Bon" invoice emails via `ReceiptParser`. Two
receipts forwarded from Gmail were imported successfully (visible in the app),
but every line item was stored with `unit_price_cents = 0` and
`line_total_cents = 0`.

Root cause: when Gmail forwards an email, its HTML renderer normalizes the
markup and wraps every `<tr>` in the invoice's price tables with an implicit
`<tbody>` element — something the original Picnic HTML does not have.
`ReceiptParser._extract_prices` looks for price rows using
`price_table.find_all("tr", recursive=False)`, which only matches `<tr>`
elements that are **direct** children of the `<table>`. With an intervening
`<tbody>`, this returns an empty list, so no prices are found and every item
falls back to the "free item" case (`line_total_cents = 0`).

Item name and quantity extraction are unaffected because they use recursive
lookups (`select_one`, `get_text`), which find elements regardless of
intervening `<tbody>` wrappers.

## Acceptance Criteria

### AC-008-01: Extract prices when price table rows are wrapped in `<tbody>`

```gherkin
Given the HTML of a Picnic invoice where the price table's rows are wrapped
  in a <tbody> element (as produced by Gmail's forwarding renderer)
When ReceiptParser.parse() is called
Then the affected item's unit_price_cents and line_total_cents are extracted
  correctly, matching the values that would be extracted from the
  original (non-wrapped) HTML
```

### AC-008-02: No regression for the original (non-wrapped) invoice HTML

```gherkin
Given the existing picnic_receipt.html fixture (no <tbody> wrapping, as in
  the original Picnic email)
When ReceiptParser.parse() is called
Then all items and the stated total are extracted exactly as before
  (TC-002-03, TC-002-04, TC-002-06 continue to pass unchanged)
```

## Notes

**Implementation approach:**
- `ReceiptParser._extract_prices` must locate price rows whether they are
  direct `<tr>` children of the price `<table>` or wrapped in a single
  `<tbody>` child — both layouts must yield the same result.
- No change to `_parse_item_row`'s row/quantity/name lookups — those already
  work via recursive selectors.

**Out of Scope:**
- General HTML-normalization handling beyond `<tbody>` wrapping of price
  tables (no other forwarding-induced structural changes have been observed).
- Re-parsing of the two already-imported (zero-price) receipts — this
  requires resetting `processed = False` on existing production data and is
  a manual follow-up step for the developer (per CLAUDE.md, DB data changes
  in production are reviewed by a human, not automated by Claude).

**Testing Strategy:**
- New fixture `picnic_receipt_forwarded.html`: a small excerpt (2 items —
  one discounted item, one "gratis" item with no price) with `<tbody>`
  wrapping the price table rows, matching what Gmail produces when
  forwarding a "Dein Bon" email.
- See TEST-008.
