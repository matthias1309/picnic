# REQ-024 — Product Categories and Spending by Category

**Status:** draft
**Created:** 2026-08-27
**Traced by:** ARCH-024, TEST-024, CR-024

## User Story

As the **account owner**,
I want **every article to belong to a product category, and my spending to be
broken down and filterable by those categories**,
in order to **see where my grocery money actually goes (drinks, dairy, household
…) instead of only a single monthly total**.

## Context

`Product` (`backend/models.py`) currently carries nothing but an exact `name`.
All statistics from REQ-004 therefore aggregate either over *everything*
(`/api/stats/spending`, `/api/stats/summary`) or over a *single article*
(`/api/stats/top-items`, `/api/stats/price-trend/{product_id}`). There is no
middle level of aggregation, which is the level a household actually budgets on.

This REQ introduces a fixed set of categories defined in code, assigns them to
products by keyword rules at parse time (correctable by hand), and adds a
spending-per-category breakdown plus a category filter for the existing
spending and top-items statistics.

Deliberate constraints, following CLAUDE.md ("no fuzzy product matching" in
Phase 1): the rules are plain, case-insensitive keyword matches over the exact
product name — deterministic, inspectable and unit-testable. A manual
assignment always wins over a rule and is never overwritten again.

## Acceptance Criteria

### AC-024-01: A new product is categorised by rule on creation

```gherkin
Given no product named "Bio Vollmilch 3,8% 1L" exists
And a keyword rule maps "milch" to the category "dairy"
When a receipt containing "Bio Vollmilch 3,8% 1L" is parsed
Then the created product has category_key "dairy"
And the assignment is marked as rule-based, not manual
```

### AC-024-02: A product without a matching rule stays uncategorised

```gherkin
Given no keyword rule matches the product name "Ahoi-Brause Sortiment"
When a receipt containing that article is parsed
Then the created product has no category_key
And it is reported under the "Nicht zugeordnet" bucket in statistics
```

### AC-024-03: The user can assign a category by hand

```gherkin
Given the product "Ahoi-Brause Sortiment" is uncategorised
When the user selects the category "Süßwaren" for it in the article list
Then PUT /api/products/{product_id}/category is sent with category_key "sweets"
And the product is stored with category_key "sweets", marked as a manual assignment
And the article list shows the new category without a page reload
```

### AC-024-04: A manual assignment is never overwritten by a rule

```gherkin
Given the product "Kokosmilch 400ml" was manually assigned to "pantry"
And a keyword rule maps "milch" to "dairy"
When the rule-based categorisation runs again over all products
Then the product still has category_key "pantry"
And it is still marked as a manual assignment
```

### AC-024-05: Existing products are categorised by a repeatable backfill

```gherkin
Given the database already contains products from earlier receipts
When the categorisation backfill is run
Then every product whose name matches a rule receives that category
And products with a manual assignment are left untouched
And running the backfill a second time changes nothing (idempotent)
```

### AC-024-06: The available categories are served to the client

```gherkin
Given the client is authenticated
When it requests GET /api/categories
Then the fixed list of categories is returned
And each entry has a stable key and a German display label
```

### AC-024-07: Spending is reported per category

```gherkin
Given receipts exist with items in several categories
When the client requests GET /api/stats/by-category
Then one bucket per category with a non-zero spend is returned
And each bucket contains category_key and total_cents
And items of uncategorised products are reported in a dedicated bucket
And the buckets are ordered by total_cents, descending
And the sum of all buckets equals the total spend over the same period
```

### AC-024-08: The category breakdown respects the requested period

```gherkin
Given receipts exist in 2026-05 and in 2026-06
When the client requests GET /api/stats/by-category with from_date=2026-06-01
  and to_date=2026-06-30
Then only line items of receipts whose effective date falls in June 2026 are counted
```

### AC-024-09: Existing statistics can be filtered by category

```gherkin
Given receipts exist with items in several categories
When the client requests GET /api/stats/spending?category=beverages
Then every bucket counts only line items of products in the "beverages" category

When the client requests GET /api/stats/top-items?category=beverages
Then only products of the "beverages" category are ranked
```

### AC-024-10: An unknown category key is rejected

```gherkin
Given the client is authenticated
When it sends PUT /api/products/{product_id}/category with category_key "nonsense"
Then a 422 response is returned
And the product's category remains unchanged

When it requests GET /api/stats/spending?category=nonsense
Then a 422 response is returned
```

### AC-024-11: The statistics page shows the category breakdown

```gherkin
Given the user is on the "Statistiken" page
When the page has loaded
Then a "Ausgaben nach Kategorie" chart is shown
And it uses the existing week/month period toggle
And an empty state is shown when no spending exists in the selected period
```

### AC-024-12: The article list is reachable and searchable

```gherkin
Given the user is logged in
When they open the "Artikel" entry in the main navigation
Then all products are listed with their current category
And a search field filters the list by product name
And each row offers a category dropdown to correct the assignment
```

## Notes

**Implementation approach:**
- Categories are a fixed constant in the backend (key + German label), not a
  database table — no CRUD UI, no delete/reassign rules needed. Proposed set:

  | `category_key` | Label |
  |---|---|
  | `fruit` | Obst |
  | `vegetables` | Gemüse |
  | `dairy` | Milchprodukte |
  | `bakery` | Backwaren |
  | `meat` | Fleisch |
  | `fish` | Fisch |
  | `frozen` | Tiefkühl |
  | `ready_meals` | Fertiggerichte |
  | `beverages` | Getränke |
  | `pantry` | Trockenware |
  | `sweets` | Süßwaren |
  | `personal_care` | Körperpflege |
  | `household` | Haushalt |
  | `other` | Sonstiges |

  A product with no assignment (`category_key IS NULL`) is reported as
  "Nicht zugeordnet" — distinct from the explicitly chosen "Sonstiges"
  (`other`).
- `products` gains `category_key VARCHAR(32) NULL` and
  `category_is_manual BOOLEAN NOT NULL DEFAULT 0`. This is a schema change and
  must be reviewed before it is applied in production (CLAUDE.md).
- The keyword rules live in a new module next to the categories constant: an
  ordered list of (keyword, category_key), matched case-insensitively as a
  substring of the product name, first match wins. Order matters and is part of
  the test spec, both for false friends (e.g. "kokosmilch" must be listed before
  "milch") and for genuinely overlapping categories: `frozen` describes how an
  article is stored, `ready_meals` what it is, so a frozen pizza matches both.
  Resolved in ARCH-024 Key Decision 3: the product type wins.
- Rule application happens where products are created today
  (`receipt_service`), plus a repeatable backfill for the existing data. The
  backfill is a maintenance script in `backend/scripts/`, in line with
  `manage_users.py`.
- Spend per category aggregates `receipt_items.line_total_cents`, joined to
  `receipts.effective_date` for the date range — the same date semantics as the
  existing statistics (REQ-018).
- All new endpoints are mounted on the authenticated `api_router` (REQ-006,
  AC-006-04).
- Frontend: a new "Artikel" page and nav entry, plus a category chart on the
  "Statistiken" page reusing `Card`, `SectionHeader` and `ToggleGroup`
  (REQ-022). `CHART_COLORS` currently holds a single `series` colour, which is
  enough for the existing single-series charts but not for a breakdown across
  14 categories: the theme needs a categorical palette with one stable colour
  per category, so that a category keeps its colour across periods and charts.

**Rejected alternatives:**
- User-manageable categories (create/rename/delete) — would require a table, a
  settings UI and reassignment rules on delete, for no gain in a single-user
  MVP.
- Correcting the category inline in the receipt detail view instead of a
  dedicated article list — makes bulk correction after the initial backfill
  impractical, since one article appears across many receipts.

**Out of Scope:**
- Per-category budgets and warnings — a follow-up REQ once the breakdown exists.
- Automatic learning of rules from manual corrections, or any fuzzy matching.
- Sub-categories / multiple categories per product — exactly one category per
  product.
- Categorising the deposit ("Pfand") rows separately — tracked as its own open
  parser topic.
