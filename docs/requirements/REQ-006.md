# REQ-006 — User Login & Authentication

**Status:** draft
**Created:** 2026-06-14
**Traced by:** ARCH-006, TEST-006

## User Story

As a household member (myself or my wife),
I want to log in with my own account before accessing the dashboard or API,
in order to keep our grocery spending data private to our household.

## Acceptance Criteria

### AC-006-01: Successful login

```gherkin
Given a registered user with a valid username and password
When they submit the login form with correct credentials
Then they receive a session and are redirected to the dashboard
```

### AC-006-02: Failed login with invalid credentials

```gherkin
Given a registered user
When they submit the login form with an incorrect username or password
Then they see an error message and remain on the login page
```

### AC-006-03: Unauthenticated access to the dashboard redirects to login

```gherkin
Given no valid session exists
When the user navigates to any dashboard route ("/", "/stats", "/receipts", "/receipts/:id")
Then they are redirected to the login page
```

### AC-006-04: Unauthenticated API requests are rejected

```gherkin
Given no valid session token is provided
When a request is made to any /picnic/api/* endpoint
Then the API responds with 401 Unauthorized
```

### AC-006-05: Session remains valid for 30 days

```gherkin
Given a user has successfully logged in
When they return to the app within 30 days without explicitly logging out
Then they remain authenticated without re-entering credentials
```

### AC-006-06: Logout

```gherkin
Given a logged-in user
When they click "Logout"
Then their session is invalidated and they are redirected to the login page
```

## Notes

- Two accounts only (the developer and his wife), stored in a new `users`
  table with hashed passwords (e.g. bcrypt/argon2). No self-registration —
  accounts are seeded manually by the developer.
- Both the React frontend and the `/picnic/api/*` backend must enforce
  authentication; a login screen alone is not sufficient if the API stays
  open.
- `/picnic/health` must remain unauthenticated, since `scripts/deploy.sh`
  polls it for the post-deploy health check.
- Session length: 30 days (long-lived), refreshed on activity — exact
  mechanism (signed cookie vs. JWT + refresh token) to be decided in ARCH.
- Password reset / account management UI is out of scope for this REQ —
  if a password needs to change, the developer updates it directly
  (e.g. via a small CLI script or DB update).
